# Bitcoin Battlefield 可行性评估

> 本文沿用自母项目 Bitcoin Battle（`~/Documents/Bitcoin Battle`），描述的是原版「Bitcoin Battlefield」和当时针对 BTC 的调研。ETH War 用同一套方案，只把标的换成 ETH。

日期：2026-10-01
对象：Newhedge「Bitcoin Battlefield」（推文 2026-09-29）

## 结论

**好实现，至少「能跑起来、看得懂」这一层不难。** 本项目（仓库根目录）已经完成主流程，全部在本机验证过：

- 7 个数据源接入，其中 6 个可用、Binance 被地区封锁
- 跨交易所成交量加权价格
- 订单簿深度换算成兵力
- 大单、爆仓、期权变成炮击
- 回合胜负判定
- 电影镜头、3 套光照、HUD

源码约 3,900 行 TypeScript 加 620 行 CSS，另有约 660 行测试和验证脚本。

真正花钱、花时间的不在技术，而在两件事：

1. **美术打磨**：原版用的是带动画的低多边形模型，加上后期处理和精细的镜头曲线。原型用的是程序生成的方块小人，画面差距主要在这里。
2. **生产级数据后端**：浏览器直接连 7 家交易所只适合做原型，正式版要改成服务端聚合后用一条 WS 推给客户端。

### 未完全验证的部分

- **实盘爆仓展示**：两次实时窗口内都没有发生 BTC 爆仓（行情平静），这条链路目前由单测和模拟覆盖。OKX 的爆仓频道已确认能实时推送（收到过其他币种的爆仓，并被正确过滤掉）。Bybit `allLiquidation` 中 `S=Buy` 表示多头被爆，这一点按官方文档实现，还没有用实盘数据核对过。
- **Binance**：当前网络下返回 HTTP 451（地区限制）。适配器已写好并测试过解析逻辑，连接失败时会按指数退避重连，指数自动排除它。换到不受限的网络后它会自动加入。
- **移动端性能**：只在 M4 桌面浏览器上测过。手机上应该用 `?q=low`，并减少兵力上限。

## 风险与注意事项

- **数据再分发条款**：把交易所行情二次展示给用户（尤其是商业 App）之前，需要确认各家 API 条款。部分交易所对商业再分发有限制。
- **指数口径**：
  - 有 24h 行情的交易所，按 24h 成交额加权。
  - Bitstamp 和 Binance 没有可用的 24h 成交额，用最近 10 分钟的成交额推算。所以 Bitstamp 刚启动时权重偏低。
  - 正式版建议在服务端统一口径。
- **大单阈值**：默认 $25K，会把同一主动单在 100ms 内的多笔成交合并后计算。行情平静时，$50K 的门槛下几十秒内可能一条流水都没有。
